## Области памяти JVM

| Область | Что хранит | Чья |
|---|---|---|
| **Стек** (stack) | кадры вызовов методов: локальные переменные примитивных типов и ссылки на объекты | у каждого потока свой |
| **Куча** (heap) | все объекты и массивы | общая для всех потоков |
| **Metaspace** | описания загруженных классов, методы, статические поля | общая |

```java
void method() {
    int count = 5;                         // значение лежит в стеке
    Person p = new Person("Анна");         // ссылка p — в стеке, объект Person — в куче
}                                          // кадр снят со стека; объект стал недостижим
```

Отсюда две разные ошибки:

- `StackOverflowError` — переполнен стек: слишком глубокая (обычно бесконечная) рекурсия;
- `OutOfMemoryError: Java heap space` — в куче нет места под новый объект, и сборщик мусора не смог ничего освободить.

Размеры задаются флагами: `-Xms` (начальный размер кучи), `-Xmx` (максимальный), `-Xss` (стек потока).

## Сборка мусора

В Java память не освобождают вручную. Сборщик мусора (GC) сам находит объекты, которые больше не нужны, и удаляет их.

«Не нужен» означает **недостижим**: до объекта нельзя добраться по цепочке ссылок от **GC roots** — корней. Корни — это локальные переменные в стеках живых потоков, статические поля загруженных классов, ссылки из нативного кода.

> **Важно.** Счётчик ссылок в JVM не используется. Два объекта, ссылающиеся друг на друга, но недоступные из корней, будут удалены — циклические ссылки проблемой не являются.

## Поколения

Наблюдение: большинство объектов живёт очень недолго. Поэтому куча поделена на поколения.

```text
Young generation                         Old generation
┌────────┬────────────┬────────────┐     ┌────────────────────────┐
│  Eden  │ Survivor 0 │ Survivor 1 │ ──► │ долгоживущие объекты   │
└────────┴────────────┴────────────┘     └────────────────────────┘
```

1. Новые объекты создаются в **Eden**.
2. Когда Eden заполняется, происходит **minor GC**: выжившие объекты копируются в Survivor, остальное пространство освобождается целиком. Это быстро, потому что живых объектов мало.
3. Объект, переживший несколько сборок, переводится в **Old generation**.
4. Когда заполняется Old, происходит **major / full GC** — намного дольше.

На время (части) сборки приложение останавливается — пауза **stop-the-world**. Цель современных сборщиков — сделать паузы короткими.

| Сборщик | Особенность |
|---|---|
| Serial | один поток; для маленьких приложений |
| Parallel | несколько потоков, максимум пропускной способности, длинные паузы |
| **G1** | по умолчанию с Java 9; куча делится на регионы, паузы предсказуемые |
| ZGC, Shenandoah | паузы порядка миллисекунды даже на огромных кучах |

## Утечки памяти в Java

GC удаляет только недостижимые объекты. Утечка — это объект, который программе уже не нужен, но ссылка на него где-то **осталась**. Типичные причины:

- **статические коллекции**, которые только растут: кеш без ограничения размера, `static Map`, куда добавляют и никогда не удаляют;
- **слушатели и колбэки**, которые подписали и забыли отписать;
- **`ThreadLocal` в пуле потоков** без `remove()`;
- **незакрытые ресурсы**: соединения, потоки ввода-вывода;
- **нестатические внутренние классы**, удерживающие внешний объект;
- **ключи `HashMap` с изменяемым `hashCode`**: запись нельзя ни найти, ни удалить.

Диагностика: снять дамп кучи (`jmap`, `-XX:+HeapDumpOnOutOfMemoryError`) и посмотреть в анализаторе (Eclipse MAT, VisualVM), кто удерживает объекты.

## Виды ссылок

| Ссылка | Когда объект удаляется | Применение |
|---|---|---|
| сильная (обычная) | никогда, пока достижим | всё |
| `SoftReference` | когда памяти не хватает | кеши |
| `WeakReference` | при ближайшей сборке | `WeakHashMap`, метаданные |
| `PhantomReference` | уже удалён; уведомление в очередь | освобождение нативных ресурсов |

## Что нельзя делать

- Рассчитывать на `System.gc()` — это лишь просьба, JVM может её проигнорировать.
- Использовать `finalize()` — устарел: момент вызова не определён. Для ресурсов есть try-with-resources.

@@ quiz
@@ q
Где хранится объект, созданный строкой `Person p = new Person();` внутри метода?
- [ ] Объект и ссылка — в стеке
- [x] Объект — в куче, ссылка `p` — в стеке
- [ ] Объект и ссылка — в куче
- [ ] В Metaspace
@@ explain
Все объекты создаются в куче. В кадре стека лежит только локальная переменная-ссылка. (JIT может в отдельных случаях разместить объект на стеке благодаря escape-анализу, но это невидимая оптимизация.)

@@ q
Объекты `a` и `b` ссылаются друг на друга, но больше на них никто не ссылается. Что с ними будет?
- [ ] Они останутся в памяти навсегда — это утечка
- [x] Сборщик мусора их удалит: они недостижимы из GC roots
- [ ] Будет брошен `OutOfMemoryError`
- [ ] Удалится только один из них
@@ explain
JVM определяет «мусор» по достижимости от корней, а не подсчётом ссылок. Изолированный цикл недостижим, значит подлежит удалению.

@@ q
К какой ошибке приведёт метод `int f(int n) { return f(n + 1); }`?
- [ ] `OutOfMemoryError: Java heap space`
- [x] `StackOverflowError`
- [ ] Ошибка компиляции
- [ ] Бесконечный цикл без ошибок
@@ explain
Каждый вызов добавляет кадр в стек потока. Условия выхода нет, стек переполняется. Куча тут ни при чём — объекты не создаются.

@@ q
Какой из сценариев является утечкой памяти в Java?
- [ ] Создание миллиона временных строк в цикле
- [ ] Два объекта ссылаются друг на друга
- [x] В статическую `Map` постоянно добавляют записи и никогда не удаляют
- [ ] Вызов метода с большим числом локальных переменных
@@ explain
Статическое поле — корень GC, поэтому всё, что лежит в такой мапе, достижимо и никогда не будет удалено. Временные объекты и циклы сборщик убирает без проблем.

@@ q
Что гарантирует вызов `System.gc()`?
- [ ] Немедленную полную сборку мусора
- [ ] Освобождение всей неиспользуемой памяти
- [x] Ничего: это лишь рекомендация JVM выполнить сборку
- [ ] Вызов `finalize()` у всех объектов
@@ explain
JVM вправе проигнорировать вызов (а с флагом `-XX:+DisableExplicitGC` — обязана). Управлять памятью через `System.gc()` нельзя.
