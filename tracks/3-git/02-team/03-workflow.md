## .gitignore

В репозитории хранят **исходники**, а не то, что из них получается. Не коммитят:

- результаты сборки: `target/`, `build/`, `*.class`, `*.jar`;
- зависимости, которые скачиваются: `node_modules/`;
- настройки IDE: `.idea/`, `*.iml`, `.vscode/`;
- локальную конфигурацию и **секреты**: `.env`, `application-local.yml`, ключи, пароли;
- логи и временные файлы.

Файл `.gitignore` в корне проекта перечисляет шаблоны игнорируемых путей:

```text
# комментарий
target/           # папка целиком
*.log             # все файлы с расширением .log
.env
!keep.log         # исключение из правила выше
/config.local     # только в корне репозитория
```

> **Ловушка.** `.gitignore` действует только на файлы, которые Git ещё **не отслеживает**. Если файл уже закоммичен, добавление его в `.gitignore` ничего не изменит. Сначала нужно убрать его из индекса, оставив на диске: `git rm --cached файл` (для папки — `git rm -r --cached папка`), и закоммитить.

> **Важно.** Пароль или ключ, попавший в коммит, считается **скомпрометированным**, даже если следующим коммитом вы его удалили: он остался в истории, а в публичном репозитории его за минуты находят сканеры. Единственное правильное действие — отозвать и заменить ключ.

## Хорошее сообщение коммита

Сообщение читают при поиске причин ошибки через полгода. Правила:

- первая строка — краткая суть, до ~50 символов, в повелительном наклонении: `Add order validation`, `Исправить расчёт скидки`;
- затем пустая строка и подробности: **почему** сделано изменение (что сделано — видно из кода);
- один коммит — одно логическое изменение;
- коммит не должен ломать сборку.

Многие команды используют **Conventional Commits**: `feat: add export to CSV`, `fix: handle null email`, `refactor:`, `docs:`, `test:`, `chore:`. Часто в сообщение добавляют номер задачи: `PROJ-123 Fix login timeout`.

Плохие сообщения: `fix`, `update`, `wip`, `правки`, `asdf`.

## Рабочие процессы

**GitHub Flow** — простой и самый распространённый:

1. `main` всегда в рабочем состоянии и готова к выкладке;
2. каждая задача — в короткоживущей ветке от `main`;
3. pull request → ревью и автотесты → слияние → выкладка.

**Git Flow** — для продуктов с версиями и редкими релизами: постоянные ветки `main` (релизы) и `develop` (разработка), плюс временные `feature/*`, `release/*`, `hotfix/*`. Мощно, но тяжеловесно.

**Trunk-Based Development** — все часто (минимум раз в день) вливают маленькие изменения в основную ветку; недоделанное прячут за переключателями функций (feature flags). Требует хороших автотестов.

## Способы слияния pull request

| Способ | Что получается в `main` |
|---|---|
| Merge commit | все коммиты ветки + коммит слияния |
| Squash and merge | один коммит со всеми изменениями ветки |
| Rebase and merge | коммиты ветки, перенесённые поверх `main`, без коммита слияния |

Squash удобен, когда в ветке много мелких коммитов вида «поправил после ревью».

## Полезные мелочи

- `git commit -am "..."` — добавить изменения отслеживаемых файлов и закоммитить (новые файлы не берёт).
- `git log --oneline --graph --all` — быстро увидеть всю картину веток.
- `git bisect` — двоичным поиском по истории находит коммит, сломавший программу.
- `git blame файл` — кто и в каком коммите последним менял каждую строку.

> **На собеседовании.** Спросят: «Как вы работаете с Git в команде?» — опишите процесс с ветками задач и pull request. «Что делать, если закоммитил пароль?» — отозвать пароль, затем чистить историю. «merge или rebase?» — rebase для своей локальной ветки, merge для общих.

@@ task gitignore | Игнорирование файлов | xp=35
В рабочей папке лежат: `app.txt` (исходник), папка `build/` с результатами сборки, файл `debug.log` и файл `.env` с секретами. Репозиторий создан, коммитов ещё нет.

Создайте `.gitignore`, который исключает папку `build/`, все файлы `*.log` и файл `.env`, и сделайте коммит с сообщением `Initial commit`, в который попадут только `app.txt` и `.gitignore`.
@@ hint

@@ hint
После создания `.gitignore` команда `git add .` добавит только неигнорируемые файлы.

@@ solution

@@ task untrack | Перестать отслеживать файл | xp=45 interview
Файл `.env` с секретами по ошибке закоммичен. Сделайте так, чтобы Git перестал его отслеживать:

- файл `.env` должен **остаться на диске**;
- он должен быть добавлен в `.gitignore`;
- изменения нужно закоммитить с сообщением `Stop tracking .env`;
- после этого `git status` должен быть чистым.
@@ hint
Убрать файл из индекса, не удаляя с диска: `git rm --cached .env`.
@@ hint
Затем `echo ".env" >> .gitignore`, `git add .gitignore` и `git commit -m "Stop tracking .env"`.
@@ starter
git ls-files
@@ solution
git rm --cached .env
echo ".env" >> .gitignore
git add .gitignore
git commit -m "Stop tracking .env"
