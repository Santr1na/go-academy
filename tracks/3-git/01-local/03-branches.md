## Ветка — это указатель

Ветка в Git — не копия проекта, а просто **именованный указатель на коммит** (файл с хешем из 40 символов). Поэтому ветки создаются мгновенно и ничего не стоят.

```text
            main
              ↓
A ← B ← C ← D
         ↖
           E ← F
               ↑
            feature   ← HEAD (текущая ветка)
```

Когда вы делаете коммит, указатель текущей ветки сдвигается на новый коммит. `HEAD` показывает, на какой ветке вы сейчас.

```bash
git branch                 # список веток
git switch -c feature      # создать ветку и перейти на неё (старый вариант: git checkout -b)
git switch main            # перейти на существующую
git branch -d feature      # удалить слитую ветку (-D — удалить принудительно)
```

Если перейти на конкретный коммит, а не на ветку (`git checkout <хеш>`), получится состояние **detached HEAD**: коммиты, сделанные в нём, не принадлежат ни одной ветке и будут потеряны при переходе, если не создать для них ветку.

## Слияние: fast-forward

```bash
git switch main
git merge feature
```

Если в `main` с момента ответвления не появилось новых коммитов, Git просто **передвигает указатель** `main` вперёд. Нового коммита не создаётся.

```text
до:    A ← B (main) ← C ← D (feature)
после: A ← B ← C ← D (main, feature)
```

## Слияние: merge-коммит

Если обе ветки ушли вперёд, Git создаёт **коммит слияния** с двумя родителями:

```text
A ← B ← C ───── M (main)
     ↖         ↙
       D ← E (feature)
```

Флаг `--no-ff` заставляет создавать merge-коммит всегда — так в истории видно, что работа велась в отдельной ветке.

## Конфликт

Конфликт возникает, когда в двух ветках **по-разному изменён один и тот же участок** файла. Git останавливает слияние и помечает спорное место:

```text
<<<<<<< HEAD
цвет = синий
=======
цвет = красный
>>>>>>> feature
```

Выше `=======` — вариант текущей ветки, ниже — вливаемой. Как разрешить:

1. Откройте файл и приведите его к нужному виду: оставьте один вариант, оба или напишите третий.
2. **Удалите все маркеры** `<<<<<<<`, `=======`, `>>>>>>>`.
3. `git add файл` — так вы сообщаете, что конфликт решён.
4. `git commit` — завершить слияние.

Передумали — `git merge --abort` вернёт всё к состоянию до слияния.

> **Ловушка.** Git считает конфликт решённым, как только вы сделали `git add`. Он не проверяет, убраны ли маркеры: забытые `<<<<<<<` спокойно попадут в коммит и сломают сборку. Перед коммитом просматривайте `git diff --staged`.

Изменения в **разных** файлах или в разных местах одного файла Git сливает сам — конфликта нет.

## Как уменьшить число конфликтов

- Делайте короткоживущие ветки и маленькие pull request-ы.
- Регулярно подтягивайте свежий `main` в свою ветку.
- Не смешивайте в одном коммите форматирование всего файла и содержательные правки.

@@ quiz
@@ q
Что такое ветка в Git?
- [ ] Копия всех файлов проекта
- [ ] Отдельная папка внутри `.git`
- [x] Перемещаемый указатель на коммит
- [ ] Список изменённых файлов
@@ explain
Ветка — это всего лишь ссылка на один коммит; история восстанавливается по цепочке родителей. Поэтому создание ветки не копирует файлы и занимает мгновение.

@@ q
От `main` создана ветка `feature`, в ней сделано два коммита. В `main` новых коммитов нет. Что произойдёт при `git switch main && git merge feature`?
- [x] Указатель `main` передвинется на последний коммит `feature` (fast-forward)
- [ ] Будет создан merge-коммит с двумя родителями
- [ ] Возникнет конфликт
- [ ] Ветка `feature` будет удалена
@@ explain
История линейна, сливать нечего — Git просто перемещает указатель вперёд. Merge-коммит создаётся, когда ветки разошлись, либо при флаге `--no-ff`.

@@ q
Когда при слиянии возникает конфликт?
- [ ] Всегда, когда в обеих ветках есть новые коммиты
- [ ] Когда в ветках изменены разные файлы
- [x] Когда в обеих ветках по-разному изменены одни и те же строки файла
- [ ] Когда ветки созданы разными людьми
@@ explain
Независимые изменения Git объединяет сам. Вмешательство человека нужно, только когда Git не может решить, какой из двух вариантов одного участка оставить.

@@ q
Вы разрешили конфликт в редакторе. Какие команды завершают слияние?
- [ ] `git merge --continue --force`
- [x] `git add <файл>`, затем `git commit`
- [ ] `git restore <файл>`
- [ ] `git branch -d`
@@ explain
`git add` помечает файл как разрешённый, `git commit` создаёт коммит слияния. Отменить незавершённое слияние можно через `git merge --abort`.

@@ task conflict | Разрешение конфликта | xp=50 interview
В ветках `main` и `feature` по-разному изменена одна и та же строка файла `config.txt`: в `main` там `color=blue`, в `feature` — `color=red`. Вы находитесь в `main`.

Влейте `feature` в `main` и разрешите конфликт: в итоговом файле должна остаться единственная строка `color=red`. Завершите слияние коммитом.
@@ hint
`git merge feature` остановится с конфликтом. Файл можно целиком перезаписать нужным содержимым: `echo "color=red" > config.txt`.
@@ hint
Затем `git add config.txt` и `git commit -m "Merge feature"`. Есть и короткий путь взять версию вливаемой ветки: `git checkout --theirs config.txt`.

@@ solution
git merge feature

git add config.txt
git commit -m "Merge feature"
