@@ card spring-vs-boot
Чем Spring Boot отличается от Spring Framework?
@@ answer
Spring Framework — набор библиотек (контейнер, MVC, данные, безопасность), требующий ручной настройки. Spring Boot — надстройка, упрощающая запуск:

- **стартеры** — согласованные наборы зависимостей;
- **автоконфигурация** — бины создаются автоматически по содержимому classpath и свойствам;
- **встроенный сервер** — приложение запускается как обычный jar;
- внешняя конфигурация (`application.yml`, профили, переменные окружения);
- Actuator: проверки состояния и метрики.

Boot не заменяет Spring, а настраивает его разумными значениями по умолчанию.

@@ card autoconfiguration
Как работает автоконфигурация? Что делает `@SpringBootApplication`?
@@ answer
`@SpringBootApplication` объединяет `@SpringBootConfiguration`, `@EnableAutoConfiguration` и `@ComponentScan` (сканирование от пакета главного класса вниз).

Автоконфигурация: Boot читает из библиотек список классов конфигурации (файл `AutoConfiguration.imports`). Каждый включается **по условию**:

- `@ConditionalOnClass` — в classpath есть нужный класс;
- `@ConditionalOnMissingBean` — разработчик не объявил свой бин;
- `@ConditionalOnProperty` — задано свойство.

Поэтому добавление стартера приносит готовые бины, а объявление собственного бина того же типа отключает автоматический.

**Что добавить.** Отчёт о сработавших условиях показывает запуск с `--debug`.

@@ card transactional
Как работает `@Transactional`? Какие у него подводные камни?
@@ answer
Spring оборачивает бин в прокси: перед вызовом метода открывается транзакция, после нормального завершения — фиксируется, при исключении — откатывается.

Подводные камни:

1. **Вызов метода того же класса** (`this.method()`) идёт мимо прокси — транзакция не открывается.
2. Аннотация на **`private`/`final`** методе не работает.
3. Откат по умолчанию только при **непроверяемых** исключениях; для проверяемых нужен `rollbackFor`.
4. Пойманное и не проброшенное исключение отката не вызывает.
5. Бин, созданный через `new`, прокси не имеет.

**Что добавить.** Propagation: `REQUIRED` (по умолчанию — присоединиться или создать), `REQUIRES_NEW` (всегда новая), и другие. `readOnly = true` — для запросов на чтение.

@@ card rest
Что такое REST? Какие HTTP-методы и коды ответов вы используете?
@@ answer
REST — архитектурный стиль API поверх HTTP: ресурсы обозначаются адресами, действия — методами, сервер не хранит состояние клиента между запросами.

| Метод | Действие | Идемпотентен |
|---|---|---|
| GET | чтение | да |
| POST | создание | нет |
| PUT | полная замена | да |
| PATCH | частичное изменение | не обязательно |
| DELETE | удаление | да |

Коды: `200` OK, `201` Created, `204` No Content, `400` некорректный запрос, `401` не аутентифицирован, `403` нет прав, `404` не найдено, `409` конфликт, `500` ошибка сервера.

**Что добавить.** Адреса — существительные во множественном числе (`/orders/42/items`), версия в пути (`/api/v1`), единый формат ошибок.

@@ card controller-flow
Как Spring MVC обрабатывает HTTP-запрос? Чем `@RestController` отличается от `@Controller`?
@@ answer
1. Запрос проходит цепочку фильтров (включая Spring Security).
2. Попадает в `DispatcherServlet` — единую точку входа.
3. `HandlerMapping` находит метод контроллера по адресу и HTTP-методу.
4. Аргументы подготавливаются: `@PathVariable`, `@RequestParam`, `@RequestBody` (JSON → объект через Jackson), валидация `@Valid`.
5. Вызывается метод контроллера.
6. Результат преобразуется в JSON и записывается в ответ. Исключения перехватывает `@ControllerAdvice`.

`@Controller` возвращает имя представления (HTML-шаблона). `@RestController` = `@Controller` + `@ResponseBody`: результат метода пишется прямо в тело ответа.

@@ card exception-handling
Как организовать обработку ошибок в REST API на Spring?
@@ answer
- Сервисы бросают собственные непроверяемые исключения (`NotFoundException`, `ConflictException`) и ничего не знают про HTTP.
- Один класс с `@RestControllerAdvice` содержит методы `@ExceptionHandler`, которые превращают исключения в ответы с нужным кодом и единым телом ошибки.
- Ошибки валидации (`MethodArgumentNotValidException`) превращаются в `400` с перечнем полей.
- Обработчик `Exception.class` — запасной: логирует стек и отвечает `500` без внутренних подробностей.

**Что добавить.** Стандартный формат ошибок — Problem Details (`ProblemDetail` в Spring 6). Стек вызовов и текст SQL клиенту не отдают.

@@ card jpa-hibernate
Что такое JPA и Hibernate? Какие состояния бывают у сущности?
@@ answer
**JPA** — спецификация ORM: отображение объектов на таблицы. **Hibernate** — её реализация. **Spring Data JPA** — надстройка, генерирующая репозитории по интерфейсам.

Состояния сущности:

- **transient** — новый объект, не связан с базой;
- **managed** — отслеживается контекстом персистентности; изменения автоматически записываются при фиксации (dirty checking);
- **detached** — контекст закрыт, изменения не отслеживаются;
- **removed** — помечена на удаление.

**Что добавить.** Контекст персистентности — кеш первого уровня в пределах транзакции: повторный `findById` той же сущности не идёт в базу.

@@ card lazy-eager
Чем ленивая загрузка отличается от жадной? Что такое `LazyInitializationException`?
@@ answer
**EAGER** — связанные данные загружаются сразу вместе с сущностью. **LAZY** — при первом обращении к ним.

По умолчанию: `@ManyToOne` и `@OneToOne` — EAGER, `@OneToMany` и `@ManyToMany` — LAZY. Рекомендуется ставить LAZY везде и загружать связи явно (`JOIN FETCH`, `@EntityGraph`).

`LazyInitializationException` возникает при обращении к ленивой связи после закрытия сессии — например, когда сущность сериализуется в контроллере вне транзакции. Решение: загрузить нужные данные внутри транзакции и вернуть DTO.

**Что добавить.** Обход ленивой связи в цикле порождает проблему N+1.

@@ card security-basics
Как устроен Spring Security? Чем аутентификация отличается от авторизации?
@@ answer
**Аутентификация** — установление личности («кто вы?», при неудаче `401`). **Авторизация** — проверка прав («что вам можно?», при неудаче `403`).

Spring Security — **цепочка фильтров** перед `DispatcherServlet`. Фильтры извлекают учётные данные (сессия, заголовок `Authorization`), проверяют их и помещают `Authentication` в `SecurityContext`. Затем правила (`authorizeHttpRequests`, `@PreAuthorize`) решают, пускать ли запрос.

**Что добавить.** Пароли хранят в виде хеша BCrypt или Argon2. JWT — подписанный токен: stateless-аутентификация без хранения сессий; содержимое токена не зашифровано, поэтому секреты в него не кладут.

@@ card testing
Как вы тестируете Spring-приложение?
@@ answer
- **Модульные тесты** сервисов: JUnit 5 + Mockito, без контекста Spring — зависимости передаются в конструктор как моки. Быстрые, их большинство.
- **Срезовые тесты**: `@WebMvcTest` — контроллеры с `MockMvc`; `@DataJpaTest` — репозитории.
- **Интеграционные**: `@SpringBootTest` поднимает весь контекст; базу удобно запускать через Testcontainers.

**Что добавить.** Пирамида тестирования: много модульных, меньше интеграционных, совсем мало сквозных. `@MockBean` / `@MockitoBean` подменяет бин в контексте. Хороший тест проверяет поведение, а не детали реализации.
