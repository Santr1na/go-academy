@@ card merge-rebase
Чем merge отличается от rebase? Когда что использовать?
@@ answer
`merge` объединяет ветки, создавая коммит слияния с двумя родителями; существующие коммиты не меняются, история сохраняется как была.

`rebase` переносит коммиты ветки поверх другой ветки, создавая **новые** коммиты с новыми хешами; история получается линейной.

**Правило.** Rebase — для своей локальной, ещё не опубликованной ветки (подтянуть свежий `main`, привести коммиты в порядок). Merge — для общих веток. Переписывать опубликованную историю нельзя: у коллег останутся старые коммиты, и истории разойдутся.

@@ card reset-revert
Чем отличаются `git reset`, `git revert` и `git restore`?
@@ answer
- `git restore файл` — отменить изменения в рабочей папке; с `--staged` — убрать файл из индекса.
- `git reset <коммит>` — передвинуть ветку назад. `--soft` оставляет изменения в индексе, `--mixed` (по умолчанию) — в рабочей папке, `--hard` — удаляет их. Переписывает историю.
- `git revert <коммит>` — создать **новый** коммит, отменяющий изменения указанного. Историю не переписывает.

**Правило.** Для уже опубликованных коммитов — только `revert`. `reset` — для локальных.

@@ card fetch-pull
Чем `git fetch` отличается от `git pull`?
@@ answer
`git fetch` скачивает новые коммиты с сервера и обновляет отслеживающие ветки (`origin/main`), но **не трогает** ваши локальные ветки и файлы.

`git pull` = `fetch` + слияние (`merge`) полученных изменений в текущую ветку. `git pull --rebase` вместо слияния переносит ваши локальные коммиты поверх полученных — история остаётся линейной.

**Что добавить.** `fetch` всегда безопасен: после него можно посмотреть, что пришло (`git log main..origin/main`), и только потом решать, как объединять.

@@ card conflict
Что такое конфликт слияния и как его разрешить?
@@ answer
Конфликт возникает, когда в двух ветках по-разному изменён один и тот же участок файла и Git не может выбрать вариант сам.

Порядок действий:

1. `git status` показывает конфликтующие файлы;
2. в файле между маркерами `<<<<<<<`, `=======`, `>>>>>>>` лежат оба варианта — нужно привести код к правильному виду и удалить маркеры;
3. `git add файл`;
4. `git commit` (при rebase — `git rebase --continue`).

Отменить: `git merge --abort` / `git rebase --abort`.

**Что добавить.** Конфликтов меньше, если ветки живут недолго, а `main` регулярно подтягивается в рабочую ветку.

@@ card git-areas
Какие три области есть в Git? Что делают `add` и `commit`?
@@ answer
1. **Рабочая папка** — файлы на диске.
2. **Индекс** (staging area) — подготовленное содержимое следующего коммита.
3. **Репозиторий** — история коммитов в папке `.git`.

`git add` копирует изменения из рабочей папки в индекс. `git commit` создаёт из содержимого индекса новый коммит — снимок проекта с автором, датой, сообщением и ссылкой на родителя.

**Что добавить.** Индекс позволяет собирать осмысленные коммиты: закоммитить часть изменений, оставив остальное на потом.

@@ card cherry-stash
Для чего нужны `git cherry-pick` и `git stash`?
@@ answer
`git cherry-pick <хеш>` применяет изменения одного конкретного коммита к текущей ветке, создавая новый коммит. Типичный случай — перенести исправление ошибки в релизную ветку, не забирая остальную работу.

`git stash` временно прячет незакоммиченные изменения, возвращая рабочую папку к чистому состоянию: удобно, когда нужно срочно переключиться на другую ветку. `git stash pop` возвращает спрятанное.

**Ловушка.** Обычный `stash` не сохраняет новые (неотслеживаемые) файлы — для них нужен флаг `-u`.

@@ card git-flow
Как вы работаете с Git в команде? Что такое pull request?
@@ answer
Распространённый процесс (GitHub Flow):

1. от актуального `main` создаётся ветка задачи;
2. в ней делаются небольшие осмысленные коммиты;
3. ветка отправляется на сервер, открывается **pull request** — запрос на слияние;
4. коллеги проводят ревью кода, автоматически запускаются сборка и тесты (CI);
5. после одобрения ветка вливается в `main` и удаляется.

Прямые коммиты в `main` обычно запрещены. Варианты слияния: merge-коммит, squash (все коммиты ветки в один), rebase.

**Что добавить.** Другие модели: Git Flow (ветки `develop`, `release`, `hotfix`) и trunk-based development (частые маленькие слияния в основную ветку).

@@ card secret-commit
Что делать, если вы случайно закоммитили пароль или ключ?
@@ answer
1. **Немедленно отозвать и заменить** секрет. Если коммит попал на сервер, секрет считается скомпрометированным: он остаётся в истории и в копиях репозитория.
2. Удалить секрет из кода и вынести в переменные окружения или хранилище секретов; добавить файл в `.gitignore`.
3. При необходимости вычистить историю (`git filter-repo`, BFG) — согласовав с командой, так как это переписывает историю.

**Что добавить.** Удаление файла следующим коммитом ничего не скрывает. А `.gitignore` не влияет на уже отслеживаемые файлы — их снимают с отслеживания через `git rm --cached`.
