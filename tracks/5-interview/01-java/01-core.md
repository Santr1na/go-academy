@@ card oop-principles
Назовите принципы ООП и объясните каждый своими словами.
@@ answer
Обычно называют четыре:

- **Инкапсуляция** — данные и методы, которые с ними работают, объединены в классе; внутреннее состояние скрыто (`private`), наружу торчит только контролируемый интерфейс. Это позволяет менять реализацию, не ломая остальной код, и защищает инварианты объекта.
- **Наследование** — класс-наследник получает поля и методы родителя и может их расширять. Отношение «является» (is-a).
- **Полиморфизм** — один и тот же вызов `shape.area()` выполняет разный код в зависимости от реального типа объекта. В Java реализуется через переопределение методов и интерфейсы.
- **Абстракция** — выделяем существенное и прячем детали: работаем с `List`, не думая, `ArrayList` там или `LinkedList`.

**Что добавить.** Хороший ответ не только перечисляет, но и даёт пример из практики, и упоминает, что наследованием не стоит злоупотреблять: часто композиция («имеет», has-a) лучше.

@@ card equals-hashcode
Расскажите про контракт `equals` и `hashCode`. Что будет, если переопределить только `equals`?
@@ answer
Контракт:

1. Если `a.equals(b)` — `true`, то `a.hashCode() == b.hashCode()` **обязательно**.
2. Обратное неверно: одинаковый хеш не означает равенство (это коллизия).
3. `hashCode` должен возвращать одно и то же значение, пока объект не менялся.
4. `equals` — рефлексивен, симметричен, транзитивен, согласован; `x.equals(null)` — `false`.

Если переопределить только `equals`, два «равных» объекта будут иметь разные хеши (по умолчанию хеш зависит от конкретного объекта). `HashMap` и `HashSet` сначала ищут корзину по хешу, поэтому положат такие объекты в разные корзины: `set.contains(new Point(1, 2))` вернёт `false`, хотя такой же объект в множестве есть, а в `HashSet` появятся «дубликаты».

**Что добавить.** Поля, участвующие в `equals`/`hashCode`, у ключей `HashMap` не должны меняться: изменился хеш — объект «потерялся» в своей старой корзине.

@@ card string-immutable
Почему `String` в Java неизменяемый? Что такое пул строк?
@@ answer
Объект `String` после создания изменить нельзя: любая «модификация» (`concat`, `replace`, `+`) создаёт новую строку.

Зачем так сделано:

- **Пул строк.** Одинаковые литералы хранятся в памяти один раз (`"abc" == "abc"` — `true`). Это безопасно только потому, что строку никто не может изменить.
- **Безопасность.** В строках передают пути к файлам, URL, имена классов, логины. Их нельзя подменить после проверки.
- **Потокобезопасность.** Неизменяемый объект можно свободно использовать из многих потоков.
- **Кеширование `hashCode`.** Хеш считается один раз — строки идеальны как ключи `HashMap`.

Пул строк — область в куче, куда попадают строковые литералы и строки после `intern()`. `new String("abc")` создаёт отдельный объект вне пула, поэтому `new String("abc") == "abc"` — `false`.

**Что добавить.** Для сборки строки в цикле используют `StringBuilder`, иначе на каждой итерации создаётся новый объект.

@@ card string-builder-buffer
Чем отличаются `String`, `StringBuilder` и `StringBuffer`?
@@ answer
- `String` — неизменяемая; каждая операция создаёт новый объект.
- `StringBuilder` — изменяемый буфер символов, **не** потокобезопасен, быстрый. Используется по умолчанию.
- `StringBuffer` — то же самое, но все методы `synchronized`. Потокобезопасен, медленнее; в современном коде почти не нужен.

Склейка в цикле через `+=` даёт квадратичную сложность: каждый раз копируется вся накопленная строка. `StringBuilder.append` дописывает в тот же буфер.

**Что добавить.** Одиночное выражение `a + b + c` компилятор оптимизирует сам, проблема именно в циклах.

@@ card eq-vs-equals
В чём разница между `==` и `equals`?
@@ answer
- `==` для примитивов сравнивает **значения**, для объектов — **ссылки** (один и тот же ли это объект в памяти).
- `equals` сравнивает объекты **по смыслу**, если метод переопределён (у `String`, `Integer`, коллекций — переопределён). В `Object` реализация по умолчанию — то же самое `==`.

Классические ловушки:

```java
new String("a") == new String("a")   // false: два разных объекта
Integer a = 127, b = 127;  a == b    // true: значения −128..127 кешируются
Integer c = 128, d = 128;  c == d    // false: два разных объекта
```

**Что добавить.** Объекты всегда сравнивают через `equals` (или `Objects.equals`, если возможен `null`).

@@ card abstract-vs-interface
Чем абстрактный класс отличается от интерфейса? Когда что выбирать?
@@ answer
| | Абстрактный класс | Интерфейс |
|---|---|---|
| Наследование | один родитель | можно реализовать много |
| Состояние (поля) | любые поля | только константы `public static final` |
| Конструкторы | есть | нет |
| Методы | любые | абстрактные, `default`, `static`, `private` (с Java 9) |

**Выбор.** Интерфейс описывает *способность* («умеет сравниваться», «умеет сохраняться») и не привязывает к иерархии. Абстрактный класс — общая *основа* для близких классов: общие поля и частичная реализация.

**Что добавить.** После появления `default`-методов в Java 8 разница уменьшилась, но главное осталось: у интерфейса нет состояния и множественная реализация разрешена.

@@ card overload-override
Чем перегрузка (overloading) отличается от переопределения (overriding)?
@@ answer
- **Перегрузка** — несколько методов с одним именем, но разными параметрами в одном классе. Какой вызвать, решает **компилятор** по типам аргументов (статическое связывание).
- **Переопределение** — наследник заменяет реализацию метода родителя с той же сигнатурой. Какой метод выполнится, решается **во время выполнения** по реальному типу объекта (динамическое связывание).

Правила переопределения: та же сигнатура; доступ нельзя сужать; возвращаемый тип тот же или подтип; нельзя добавлять новые проверяемые исключения. `static`, `private` и `final` методы переопределить нельзя (статические — «скрываются»).

**Что добавить.** Аннотация `@Override` заставляет компилятор проверить, что метод действительно что-то переопределяет.

@@ card final-finally-finalize
Что означают `final`, `finally` и `finalize`?
@@ answer
- `final` — модификатор: переменную нельзя переприсвоить, метод нельзя переопределить, от класса нельзя наследоваться.
- `finally` — блок после `try/catch`, выполняется всегда (и при исключении, и при `return`); нужен для освобождения ресурсов. Не выполнится только при `System.exit()` или гибели JVM.
- `finalize` — метод `Object`, который сборщик мусора *мог* вызвать перед удалением объекта. Устарел (deprecated с Java 9), пользоваться нельзя: момент вызова не определён.

**Ловушка.** `final List<String> list` запрещает менять ссылку, но не содержимое: `list.add("x")` работает.

@@ card exceptions-hierarchy
Расскажите про иерархию исключений. Чем checked отличаются от unchecked?
@@ answer
```text
Throwable
├── Error                 — проблемы JVM (OutOfMemoryError, StackOverflowError); не ловим
└── Exception
    ├── RuntimeException  — unchecked (NullPointerException, IllegalArgumentException…)
    └── остальные         — checked (IOException, SQLException…)
```

- **Checked** — компилятор заставляет либо поймать (`try/catch`), либо объявить в `throws`. Это ожидаемые внешние сбои: нет файла, недоступна сеть.
- **Unchecked** (`RuntimeException` и наследники) — ошибки программиста: `null`, неверный индекс, неверный аргумент. Обрабатывать не обязан.

**Что добавить.** В современном коде (и в Spring) предпочитают unchecked: checked-исключения плохо сочетаются с лямбдами и загромождают сигнатуры. Свои бизнес-исключения обычно наследуют от `RuntimeException`.

@@ card pass-by-value
Как в Java передаются параметры: по значению или по ссылке?
@@ answer
**Всегда по значению.** Для примитивов копируется само значение. Для объектов копируется **ссылка** — то есть метод получает копию ссылки на тот же объект.

Следствия:

- изменить состояние объекта через параметр можно (`list.add(1)` увидит вызывающий код);
- переприсвоить параметр (`list = new ArrayList<>()`) — бесполезно: меняется только локальная копия ссылки.

```java
void change(StringBuilder sb) { sb.append("!"); sb = new StringBuilder("new"); }
// снаружи: к исходному объекту добавился "!", замена ссылки не видна
```

**Что добавить.** Ответ «объекты передаются по ссылке» — ошибка, на которой интервьюеры любят ловить.

@@ card static-keyword
Что означает `static`? Можно ли из статического метода обратиться к нестатическому полю?
@@ answer
`static` означает «принадлежит классу, а не объекту»:

- статическое **поле** одно на весь класс, общее для всех объектов;
- статический **метод** вызывается без объекта, у него нет `this`;
- статический **блок** выполняется один раз при загрузке класса;
- статический **вложенный класс** не держит ссылку на внешний объект.

Из статического метода нельзя напрямую обратиться к нестатическому полю или методу: непонятно, чей это объект. Нужно создать объект или получить его параметром.

**Что добавить.** Статические методы не переопределяются, а скрываются: вызов определяется типом ссылки, а не объекта. Изменяемое статическое состояние — источник проблем в многопоточности и тестах.

@@ card immutable-class
Как сделать класс неизменяемым (immutable)?
@@ answer
1. Объявить класс `final` (чтобы наследник не добавил изменяемость).
2. Все поля — `private final`.
3. Не давать сеттеров и методов, меняющих состояние.
4. Для изменяемых полей (списки, даты, массивы) делать **защитные копии** в конструкторе и в геттерах: `this.items = List.copyOf(items)`.
5. «Изменяющие» операции возвращают новый объект.

Плюсы: потокобезопасность без синхронизации, безопасно использовать как ключ `HashMap`, проще рассуждать о коде.

**Что добавить.** С Java 16 для таких классов есть `record` — он генерирует конструктор, геттеры, `equals`, `hashCode`, `toString`. Но защитные копии изменяемых полей всё равно на вас.
