@@ card hashmap-internals
Как устроен `HashMap`? Что происходит при вызове `put`?
@@ answer
Внутри — массив **корзин** (buckets). При `put(key, value)`:

1. Вычисляется `key.hashCode()`, старшие биты подмешиваются к младшим.
2. По хешу вычисляется индекс корзины: `(n - 1) & hash`, где `n` — размер массива (всегда степень двойки).
3. Если корзина пуста — туда кладётся узел. Если нет — это **коллизия**: узлы корзины перебираются, ключи сравниваются по хешу и `equals`. Нашли равный ключ — значение заменяется, не нашли — добавляется новый узел.
4. Корзина — связный список; когда в ней больше 8 узлов (и массив не меньше 64), список превращается в **красно-чёрное дерево** (Java 8+), чтобы поиск был O(log n), а не O(n).
5. Когда элементов больше `capacity × loadFactor` (по умолчанию 16 × 0.75 = 12), массив увеличивается вдвое и элементы перераспределяются (resize).

Сложность `get`/`put` — в среднем O(1).

**Что добавить.** Допускается один `null`-ключ (корзина 0). `HashMap` не потокобезопасен и не гарантирует порядок.

@@ card arraylist-linkedlist
`ArrayList` или `LinkedList`: в чём разница и что выбрать?
@@ answer
| Операция | `ArrayList` (массив) | `LinkedList` (двусвязный список) |
|---|---|---|
| Доступ по индексу | O(1) | O(n) |
| Добавление в конец | O(1) амортизированно | O(1) |
| Вставка/удаление в середине | O(n) — сдвиг элементов | O(n) — поиск узла, сама вставка O(1) |
| Память | компактно | на каждый элемент узел с двумя ссылками |

На практике почти всегда выбирают `ArrayList`: он дружит с кешем процессора и занимает меньше памяти. `LinkedList` выигрывает редко — когда много вставок/удалений в начале или через итератор. Для очереди и стека лучше `ArrayDeque`.

**Что добавить.** `ArrayList` растёт в 1,5 раза при переполнении; если размер известен — задайте начальную ёмкость.

@@ card hashmap-key-mutable
Что будет, если изменить объект, который используется как ключ в `HashMap`?
@@ answer
Если изменились поля, участвующие в `hashCode`, хеш ключа станет другим. Запись при этом останется в **старой** корзине. `get` с тем же объектом вычислит новый хеш, пойдёт в другую корзину и вернёт `null`. Запись «потеряна»: она занимает память, но достать её нельзя (разве что перебором всех записей).

Вывод: ключи должны быть **неизменяемыми** (`String`, `Integer`, `record`, enum) либо как минимум не меняться, пока лежат в мапе.

@@ card hashmap-vs-others
Чем отличаются `HashMap`, `LinkedHashMap`, `TreeMap` и `Hashtable`?
@@ answer
- `HashMap` — порядок не гарантирован; O(1); один `null`-ключ.
- `LinkedHashMap` — хранит порядок вставки (или порядок доступа — удобно для LRU-кеша); чуть больше памяти.
- `TreeMap` — ключи отсортированы (красно-чёрное дерево); операции O(log n); есть `firstKey`, `floorKey`, `headMap`; `null`-ключ нельзя.
- `Hashtable` — устаревший, все методы `synchronized`, `null` запрещён. Вместо него — `ConcurrentHashMap`.

**Что добавить.** Аналогично для множеств: `HashSet` / `LinkedHashSet` / `TreeSet` — они построены поверх соответствующих мап.

@@ card concurrent-modification
Что такое `ConcurrentModificationException` и как её избежать?
@@ answer
Исключение бросает итератор, когда обнаруживает, что коллекцию изменили в обход него во время обхода (fail-fast). Потоки тут ни при чём — хватает одного:

```java
for (String s : list) {
    if (s.isEmpty()) list.remove(s);   // ConcurrentModificationException
}
```

Как правильно удалять при обходе:

- `list.removeIf(String::isEmpty)`;
- явный итератор и `it.remove()`;
- собрать новую коллекцию (например, через Stream и `filter`).

**Что добавить.** Коллекции из `java.util.concurrent` (`CopyOnWriteArrayList`, `ConcurrentHashMap`) имеют fail-safe/слабо согласованные итераторы и это исключение не бросают.

@@ card comparable-comparator
Чем `Comparable` отличается от `Comparator`?
@@ answer
- `Comparable<T>` — интерфейс, который реализует **сам класс**: метод `compareTo` задаёт «естественный» порядок (у `String` — лексикографический, у чисел — по возрастанию). Порядок один.
- `Comparator<T>` — **отдельный** объект с методом `compare(a, b)`. Позволяет задать сколько угодно порядков, не меняя класс.

```java
people.sort(Comparator.comparing(Person::getAge).thenComparing(Person::getName).reversed());
```

Контракт: отрицательное число — первый меньше, 0 — равны, положительное — больше.

**Ловушка.** Писать `return a.x - b.x` опасно из-за переполнения — используйте `Integer.compare(a.x, b.x)`. И порядок желательно согласовать с `equals`, иначе `TreeSet` будет вести себя неожиданно.

@@ card fail-fast-set
Как `HashSet` проверяет, что элемент уже есть? Что нужно, чтобы свои объекты корректно работали в `HashSet`?
@@ answer
`HashSet` — обёртка над `HashMap`: элементы хранятся как ключи. При `add` вычисляется `hashCode`, находится корзина, внутри неё элемент сравнивается с имеющимися через `equals`. Нашёлся равный — `add` возвращает `false`.

Значит, у своих классов должны быть согласованно переопределены **и `equals`, и `hashCode`**, причём по одним и тем же полям, и эти поля не должны меняться, пока объект в множестве.

@@ card collection-hierarchy
Опишите иерархию Collection Framework.
@@ answer
```text
Iterable
└── Collection
    ├── List   — порядок, индексы, дубликаты: ArrayList, LinkedList
    ├── Set    — без дубликатов: HashSet, LinkedHashSet, TreeSet (SortedSet)
    └── Queue  — очереди: PriorityQueue, Deque → ArrayDeque, LinkedList

Map (не наследует Collection) — пары ключ–значение: HashMap, LinkedHashMap, TreeMap
```

**Что добавить.** `Map` не входит в `Collection`, но является частью фреймворка. Вспомогательные классы: `Collections` (сортировка, неизменяемые обёртки) и `Arrays`. С Java 9 есть фабрики `List.of`, `Set.of`, `Map.of` — они возвращают неизменяемые коллекции и не принимают `null`.

@@ card concurrenthashmap
Как работает `ConcurrentHashMap` и чем он лучше `Collections.synchronizedMap`?
@@ answer
`synchronizedMap` оборачивает каждый метод в один общий замок: в любой момент с мапой работает только один поток.

`ConcurrentHashMap` (Java 8+) блокирует не всю таблицу, а **отдельную корзину**: вставка в пустую корзину делается атомарной операцией CAS без блокировки, в занятую — под `synchronized` на первом узле корзины. Чтение вообще не блокируется. Поэтому много потоков работают параллельно.

Важно:

- `null` запрещён и как ключ, и как значение;
- отдельные операции атомарны, но **последовательность** `if (!map.containsKey(k)) map.put(k, v)` — нет. Используйте `putIfAbsent`, `computeIfAbsent`, `merge`;
- итераторы слабо согласованы: не бросают `ConcurrentModificationException`.

@@ card list-of-vs-aslist
Чем отличаются `Arrays.asList`, `List.of` и `new ArrayList<>(...)`?
@@ answer
- `Arrays.asList(arr)` — список фиксированного размера, «вид» на массив: `set` работает (и меняет массив), `add`/`remove` бросают `UnsupportedOperationException`. `null` допускается.
- `List.of(...)` — полностью неизменяемый список; любые изменения и `null`-элементы запрещены.
- `new ArrayList<>(коллекция)` — обычный изменяемый независимый список.

**Ловушка.** `Arrays.asList(new int[]{1, 2, 3})` даёт `List<int[]>` из одного элемента: дженерики не работают с примитивами.
