@@ card process-thread
Чем процесс отличается от потока? Как создать поток в Java?
@@ answer
**Процесс** — запущенная программа с собственным адресным пространством. **Поток** — единица выполнения внутри процесса: потоки делят общую память (кучу), но у каждого свой стек.

Создать поток: передать `Runnable` в `new Thread(runnable).start()`, унаследовать `Thread` или — как делают на практике — отправить задачу в пул: `executor.submit(task)`.

**Что важно сказать.** `start()` создаёт новый поток, а `run()` — обычный вызов метода в текущем потоке. Вручную потоки почти не создают: используют `ExecutorService`, с Java 21 — виртуальные потоки.

@@ card synchronized-volatile
В чём разница между `synchronized` и `volatile`?
@@ answer
- `synchronized` даёт **взаимное исключение** и **видимость**: в блок входит только один поток, изменения гарантированно видны следующему. Потоки могут блокироваться.
- `volatile` даёт только **видимость**: запись в переменную сразу видна всем потокам. Блокировок нет, но и атомарности составных операций нет.

`volatile int count; count++` остаётся гонкой: чтение, сложение и запись — три действия.

**Когда что.** `volatile` — для флагов и одиночных записей (`volatile boolean running`). `synchronized`, `Lock` или атомарные классы — для составных операций «прочитал — изменил — записал».

@@ card race-condition
Что такое состояние гонки и как его избежать?
@@ answer
Гонка (race condition) — ситуация, когда результат зависит от того, в каком порядке переплелись действия потоков над общими изменяемыми данными. Классический пример — `count++` из двух потоков: оба читают одно значение, и одно обновление теряется.

Способы избежать:

1. **не делить состояние**: локальные переменные, отдельные объекты на поток, `ThreadLocal`;
2. **не менять состояние**: неизменяемые объекты;
3. **синхронизировать доступ**: `synchronized`, `ReentrantLock`;
4. **атомарные операции**: `AtomicInteger`, `ConcurrentHashMap.merge`;
5. **потокобезопасные коллекции** из `java.util.concurrent`.

**Что добавить.** Синхронизировать нужно и чтение, и запись; потокобезопасность отдельных методов не делает атомарной их последовательность.

@@ card deadlock
Что такое deadlock? Как его обнаружить и предотвратить?
@@ answer
Взаимная блокировка: поток 1 держит замок A и ждёт B, поток 2 держит B и ждёт A. Оба ждут вечно; программа не падает, а «зависает».

**Предотвращение:**

- всегда захватывать замки **в одном порядке** (например, по возрастанию id) — главный приём;
- `tryLock` с таймаутом и откатом;
- не вызывать чужой код, удерживая замок;
- уменьшать число замков: неизменяемость, готовые потокобезопасные структуры.

**Обнаружение:** дамп потоков (`jstack <pid>`, `jcmd <pid> Thread.print`) прямо сообщает о найденном deadlock и показывает, кто что держит.

**Что добавить.** Родственные проблемы: livelock (потоки активны, но бесконечно уступают друг другу) и starvation (потоку не достаётся ресурс).

@@ card executor-service
Зачем нужен пул потоков? Какие виды пулов вы знаете?
@@ answer
Создание потока дорого (стек, структуры ОС), а неограниченное число потоков исчерпает память. Пул держит ограниченный набор потоков и переиспользует их; задачи ждут в очереди.

`Executors`:

- `newFixedThreadPool(n)` — фиксированное число потоков, неограниченная очередь;
- `newCachedThreadPool()` — создаёт потоки по требованию (может создать слишком много);
- `newSingleThreadExecutor()` — один поток, задачи по порядку;
- `newScheduledThreadPool(n)` — выполнение по расписанию;
- `newVirtualThreadPerTaskExecutor()` — виртуальный поток на задачу (Java 21).

**Что важно сказать.** Параметры `ThreadPoolExecutor`: core и max размер, очередь, политика отказа. Порядок: потоки до core → очередь → потоки до max → отказ. Пул нужно завершать (`shutdown`). Для вычислений потоков столько, сколько ядер; для ввода-вывода — больше.

@@ card future-completablefuture
Чем `CompletableFuture` лучше `Future`?
@@ answer
`Future` позволяет только дождаться результата блокирующим `get()`, проверить готовность или отменить задачу.

`CompletableFuture` позволяет строить **неблокирующие цепочки**:

- `thenApply` — преобразовать результат;
- `thenCompose` — продолжить другой асинхронной операцией;
- `thenCombine`, `allOf`, `anyOf` — объединить несколько задач;
- `exceptionally`, `handle` — обработать ошибку;
- его можно завершить вручную (`complete`).

**Ловушка.** По умолчанию задачи выполняются в общем `ForkJoinPool.commonPool()`; блокирующие операции в нём останавливают всё приложение. Для ввода-вывода нужно передавать собственный пул.

@@ card wait-notify
Как работают `wait()` и `notify()`? Чем `wait` отличается от `sleep`?
@@ answer
`wait()`, `notify()`, `notifyAll()` — методы `Object` для ожидания событий. Вызываются только внутри `synchronized` по тому же объекту, иначе — `IllegalMonitorStateException`.

- `wait()` **освобождает монитор** и усыпляет поток, пока его не разбудят;
- `notify()` будит один ждущий поток, `notifyAll()` — все.

Условие ожидания проверяют в цикле `while`, а не `if`: возможны ложные пробуждения, и пока поток заново захватывал монитор, условие могло измениться.

`sleep(ms)` — статический метод `Thread`: просто приостанавливает поток и **не отпускает** захваченные блокировки.

**Что добавить.** В прикладном коде вместо `wait/notify` используют `BlockingQueue`, `CountDownLatch`, `Condition`.

@@ card atomic-cas
Как работают атомарные классы? Что такое CAS?
@@ answer
`AtomicInteger`, `AtomicLong`, `AtomicReference` обеспечивают атомарные операции **без блокировок**.

В основе — процессорная операция **compare-and-swap**: «запиши новое значение, только если текущее равно ожидаемому». Если значение успел изменить другой поток, операция не проходит и повторяется в цикле:

```java
do {
    old = value.get();
    next = old + 1;
} while (!value.compareAndSet(old, next));
```

Поток не засыпает и не переключается — при умеренной конкуренции это быстрее замков.

**Что добавить.** При очень высокой конкуренции лучше `LongAdder`. Проблема ABA (значение изменилось A→B→A) решается `AtomicStampedReference`.

@@ card thread-local
Что такое `ThreadLocal` и где он применяется?
@@ answer
`ThreadLocal<T>` хранит отдельное значение для каждого потока: один и тот же объект `ThreadLocal` возвращает разным потокам разные данные.

Применение: контекст запроса — текущий пользователь (`SecurityContextHolder` в Spring Security), текущая транзакция, идентификатор запроса для логов (MDC), объекты, которые не потокобезопасны (раньше — `SimpleDateFormat`).

**Ловушка.** В пуле потоки переиспользуются. Если не вызвать `remove()` в `finally`, значение останется в потоке и «протечёт» в следующий запрос; кроме того, это утечка памяти.

@@ card happens-before
Что такое Java Memory Model и отношение happens-before?
@@ answer
Модель памяти Java определяет, когда изменения, сделанные одним потоком, **гарантированно видны** другому. Без гарантий компилятор и процессор вправе переставлять операции и держать значения в кешах.

**Happens-before** — такая гарантия: если действие A happens-before B, то B увидит результат A. Основные правила:

- освобождение монитора → следующий его захват;
- запись в `volatile`-поле → последующее чтение;
- `Thread.start()` → любые действия в запущенном потоке;
- завершение потока → возврат из `join()`;
- запись `final`-поля в конструкторе → чтение после публикации объекта.

**Практический вывод.** Если между записью и чтением общей переменной нет ни одной такой связи, читающий поток может увидеть старое значение — программа содержит гонку данных.
