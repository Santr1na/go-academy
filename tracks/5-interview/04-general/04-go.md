@@ card slice-internals
Как устроен срез в Go? Чем он отличается от массива?
@@ answer
**Массив** — значение фиксированной длины; длина входит в тип (`[3]int` и `[4]int` — разные типы), при присваивании и передаче в функцию копируется целиком.

**Срез** — небольшая структура из трёх полей: указатель на базовый массив, длина (`len`) и ёмкость (`cap`). При передаче копируется только эта структура, а базовый массив остаётся общим.

Следствия:

- изменение элементов через копию среза видно в оригинале;
- `append` при нехватке ёмкости создаёт **новый** массив, и срезы перестают быть связанными; при достаточной ёмкости — пишет в общий массив и может затереть данные соседнего среза;
- результат `append` всегда нужно присваивать: `s = append(s, x)`.

@@ card map-go
Как устроена map в Go? Какие у неё особенности?
@@ answer
`map` — хеш-таблица: массив корзин (bucket), в каждой до 8 пар; при переполнении таблица растёт и данные постепенно переносятся.

Особенности:

- нулевое значение — `nil`: читать из неё можно, **запись вызывает панику**; создавать через `make` или литерал;
- порядок обхода **случайный** — намеренно;
- чтение отсутствующего ключа возвращает нулевое значение; наличие проверяют так: `v, ok := m[k]`;
- map **не потокобезопасна**: одновременная запись приводит к аварийному завершению (`fatal error: concurrent map writes`); нужна `sync.Mutex`/`sync.RWMutex` или `sync.Map`;
- ключом может быть только сравнимый тип (срезы, map и функции — нельзя);
- нельзя взять адрес элемента: `&m[k]` не компилируется.

@@ card interface-nil
Как устроены интерфейсы в Go? Почему интерфейс, содержащий nil-указатель, не равен nil?
@@ answer
Интерфейс реализуется **неявно**: тип удовлетворяет интерфейсу, если у него есть нужные методы; ключевого слова `implements` нет.

Значение интерфейса — пара **(тип, значение)**. Интерфейс равен `nil`, только когда пусты **обе** части.

```go
var p *MyError = nil
var err error = p        // (тип *MyError, значение nil)
fmt.Println(err == nil)  // false
```

Классическая ошибка — функция возвращает типизированный nil-указатель как `error`, и проверка `if err != nil` срабатывает. Правильно — возвращать явно `return nil`.

**Что добавить.** Пустой интерфейс `any` принимает любое значение; конкретный тип достают через утверждение типа `v, ok := x.(T)` или `switch x.(type)`.

@@ card goroutines
Что такое горутина? Чем она отличается от потока ОС?
@@ answer
Горутина — легковесный поток выполнения, которым управляет среда выполнения Go, а не операционная система.

| | Горутина | Поток ОС |
|---|---|---|
| Начальный стек | ~2 КБ, растёт динамически | ~1–8 МБ |
| Создание и переключение | дёшево, в пространстве пользователя | дорого, через ядро |
| Количество | сотни тысяч | тысячи |

Планировщик Go работает по модели **GMP**: G — горутины, M — потоки ОС, P — логические процессоры (их число задаёт `GOMAXPROCS`). Горутины распределяются по потокам; при блокирующей операции поток может быть отвязан, чтобы остальные горутины продолжали работу.

**Что добавить.** `main` не ждёт завершения других горутин — нужен `sync.WaitGroup` или канал. Горутина, которая никогда не завершится, — утечка.

@@ card channels
Что такое каналы? Чем буферизованный канал отличается от небуферизованного?
@@ answer
Канал — типизированный потокобезопасный «трубопровод» для передачи значений между горутинами.

- **Небуферизованный** (`make(chan T)`): отправка блокируется, пока другая горутина не начнёт получать, — передача происходит «из рук в руки».
- **Буферизованный** (`make(chan T, n)`): отправка блокируется только при полном буфере, получение — при пустом.

Поведение, которое нужно знать:

| Операция | nil-канал | закрытый канал |
|---|---|---|
| отправка | блокируется навсегда | паника |
| получение | блокируется навсегда | нулевое значение, `ok == false` |
| закрытие | паника | паника |

Закрывает канал **отправитель**. `for v := range ch` читает до закрытия.

@@ card select-context
Для чего нужны `select` и `context`?
@@ answer
`select` ждёт сразу несколько операций с каналами и выполняет ту, что готова первой (если готовы несколько — выбирает случайно). С веткой `default` он не блокируется. Типичное применение — таймауты и отмена:

```go
select {
case res := <-results:
    use(res)
case <-ctx.Done():
    return ctx.Err()
}
```

`context.Context` передаёт по цепочке вызовов **сигнал отмены, срок и значения запроса**. `WithCancel`, `WithTimeout`, `WithDeadline` создают производный контекст; функцию `cancel` нужно вызывать всегда (`defer cancel()`), иначе утекают ресурсы.

**Правила.** Контекст — первый параметр функции, в структурах не хранится; значения в нём — только данные запроса (идентификатор трассировки), а не обычные параметры.

@@ card defer-panic
Как работают `defer`, `panic` и `recover`?
@@ answer
`defer` откладывает вызов до выхода из функции. Отложенные вызовы выполняются в порядке **LIFO**. Аргументы вычисляются **в момент** `defer`, а не при выполнении. Отложенная функция может изменить именованное возвращаемое значение.

`panic` прерывает обычное выполнение: стек раскручивается, выполняются отложенные вызовы, затем программа завершается.

`recover` останавливает панику, но работает **только внутри отложенной функции** и только в той же горутине. Паника в другой горутине, не перехваченная в ней самой, завершит всю программу.

**Что добавить.** Обычные ошибки в Go возвращают значением `error`; `panic` — для действительно невозможных ситуаций.

@@ card errors-go
Как устроена обработка ошибок в Go?
@@ answer
Ошибка — обычное значение типа `error` (интерфейс с методом `Error() string`), которое функция возвращает последним результатом. Вызывающий код обязан явно проверить: `if err != nil`.

- Контекст добавляют оборачиванием: `fmt.Errorf("загрузка профиля %d: %w", id, err)` — глагол `%w` сохраняет исходную ошибку.
- `errors.Is(err, target)` проверяет, есть ли в цепочке конкретная ошибка.
- `errors.As(err, &target)` достаёт из цепочки ошибку нужного типа.
- Сравнение `err == ErrNotFound` на обёрнутой ошибке не сработает — нужен `errors.Is`.

**Что добавить.** Ошибку нужно либо обработать, либо вернуть выше — но не то и другое сразу (например, не логировать на каждом уровне).

@@ card sync-primitives
Какие примитивы синхронизации есть в Go? Когда использовать мьютекс, а когда канал?
@@ answer
- `sync.Mutex` / `sync.RWMutex` — взаимное исключение; `RWMutex` допускает много читателей одновременно.
- `sync.WaitGroup` — дождаться завершения группы горутин.
- `sync.Once` — выполнить действие ровно один раз.
- `sync/atomic` — атомарные операции над числами и указателями.
- `sync.Pool` — переиспользование временных объектов.
- `errgroup` — группа горутин с общей ошибкой и отменой.

**Выбор.** Мьютекс — когда защищаете общее состояние (кеш, счётчик). Канал — когда передаёте данные или владение ими между горутинами, строите конвейеры, сигнализируете о событиях. Принцип Go: «не общайтесь через общую память, а делите память через общение».

**Что добавить.** Мьютекс нельзя копировать после первого использования; гонки ищут флагом `go test -race`.
