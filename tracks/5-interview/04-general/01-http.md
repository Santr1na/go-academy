@@ card url-in-browser
Что происходит, когда вы вводите адрес сайта в браузере и нажимаете Enter?
@@ answer
1. **DNS**: браузер узнаёт IP-адрес по имени домена (кеши браузера и ОС, затем DNS-сервер).
2. **TCP**: устанавливается соединение — трёхэтапное рукопожатие.
3. **TLS** (для HTTPS): проверка сертификата сервера и согласование ключей шифрования.
4. **HTTP-запрос**: метод, путь, заголовки, при необходимости тело.
5. Запрос проходит балансировщик нагрузки и попадает в приложение; оно обращается к базе и формирует ответ.
6. **HTTP-ответ**: код состояния, заголовки, тело.
7. Браузер разбирает HTML, догружает стили, скрипты и изображения, отрисовывает страницу.

**Совет.** Вопрос открытый: начните с общей схемы и углубляйтесь в ту часть, которую знаете лучше.

@@ card http-methods
Какие HTTP-методы вы знаете? Что такое идемпотентность?
@@ answer
- `GET` — получить; безопасный и идемпотентный.
- `POST` — создать или выполнить действие; не идемпотентный.
- `PUT` — заменить ресурс целиком; идемпотентный.
- `PATCH` — изменить часть ресурса.
- `DELETE` — удалить; идемпотентный.
- `HEAD`, `OPTIONS` — служебные.

**Идемпотентность**: повторное выполнение запроса даёт то же состояние, что и однократное. Это важно при повторах после сбоев сети: `PUT` и `DELETE` можно безопасно повторить, а повторный `POST` создаст дубликат (для защиты используют ключ идемпотентности).

**Безопасный** метод не изменяет состояние сервера.

@@ card status-codes
Какие группы кодов ответа HTTP существуют? Назовите основные.
@@ answer
- **1xx** — информационные.
- **2xx** — успех: `200 OK`, `201 Created`, `204 No Content`.
- **3xx** — перенаправление: `301` навсегда, `302` временно, `304 Not Modified`.
- **4xx** — ошибка клиента: `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `422`, `429 Too Many Requests`.
- **5xx** — ошибка сервера: `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`.

**Частое уточнение.** `401` — клиент не аутентифицирован; `403` — аутентифицирован, но прав нет.

@@ card http-https
Чем HTTPS отличается от HTTP?
@@ answer
HTTPS — это HTTP поверх **TLS**. Он даёт:

- **шифрование** — данные нельзя прочитать при перехвате;
- **целостность** — данные нельзя незаметно изменить;
- **аутентификацию сервера** — сертификат, подписанный удостоверяющим центром, подтверждает, что это настоящий сайт.

При установке соединения стороны с помощью асимметричной криптографии согласуют общий ключ, а дальше данные шифруются быстрым симметричным алгоритмом.

**Что добавить.** HTTP/2 мультиплексирует несколько запросов в одном соединении; HTTP/3 работает поверх UDP (QUIC).

@@ card cookies-sessions-jwt
Как сервер «помнит» пользователя? Cookie, сессии и токены.
@@ answer
HTTP не хранит состояние между запросами, поэтому личность нужно передавать с каждым запросом.

- **Сессия + cookie**: сервер хранит данные сессии, браузер автоматически отправляет cookie с её идентификатором. Легко отозвать; при нескольких серверах нужно общее хранилище (например, Redis). Требует защиты от CSRF.
- **Токен (JWT)**: клиент хранит подписанный токен и присылает его в заголовке `Authorization: Bearer …`. Сервер ничего не хранит и проверяет подпись. Легко масштабируется, но токен трудно отозвать до истечения срока — поэтому его делают короткоживущим и добавляют refresh-токен.

**Флаги cookie:** `HttpOnly` (недоступна скриптам), `Secure` (только по HTTPS), `SameSite`.

@@ card rest-principles
Что такое REST и каковы его принципы?
@@ answer
REST — архитектурный стиль взаимодействия по HTTP:

- **клиент–сервер** — разделение ответственности;
- **без состояния** — каждый запрос содержит всё необходимое, сервер не хранит контекст клиента;
- **единообразный интерфейс** — ресурсы идентифицируются адресами, действия задаются стандартными методами, обмен идёт представлениями (обычно JSON);
- **кешируемость** — ответы помечаются как кешируемые или нет;
- **слоистая система** — клиент не знает, общается он с сервером напрямую или через прокси.

**Что добавить.** Альтернативы: gRPC (бинарный протокол, строгие контракты — для связи сервисов между собой), GraphQL (клиент сам указывает нужные поля), очереди сообщений для асинхронного обмена.

@@ card tcp-udp
Чем TCP отличается от UDP?
@@ answer
**TCP** устанавливает соединение и гарантирует доставку: данные приходят целиком и в правильном порядке, потерянные пакеты отправляются повторно, есть управление перегрузкой. Цена — накладные расходы и задержки. Используется в HTTP, почте, базах данных.

**UDP** — без соединения и гарантий: пакеты могут потеряться или прийти в другом порядке, зато быстро. Используется там, где скорость важнее надёжности: видео- и аудиосвязь, игры, DNS; на нём построен HTTP/3.

@@ card cors
Что такое CORS?
@@ answer
Браузеры применяют **политику одного источника**: скрипт со страницы `https://app.com` по умолчанию не может читать ответы с `https://api.other.com`.

CORS (Cross-Origin Resource Sharing) — механизм, которым **сервер** разрешает такие запросы, возвращая заголовки `Access-Control-Allow-Origin`, `-Methods`, `-Headers`. Перед «непростыми» запросами браузер шлёт предварительный запрос `OPTIONS` (preflight).

**Важно.** CORS — ограничение браузера, а не защита сервера: запрос из `curl` или другого сервера выполнится в любом случае. В Spring настраивается через `@CrossOrigin` или глобальную конфигурацию.
