## Аутентификация и авторизация

- **Аутентификация** — «кто вы?»: проверка личности (логин и пароль, токен). Неудача — `401 Unauthorized`.
- **Авторизация** — «что вам можно?»: проверка прав. Неудача — `403 Forbidden`.

## Как устроен Spring Security

Перед `DispatcherServlet` стоит **цепочка фильтров**. Каждый запрос проходит через неё: фильтры извлекают учётные данные, проверяют их и кладут результат в `SecurityContext` — оттуда в любом месте кода можно узнать текущего пользователя.

```java
@Configuration
@EnableMethodSecurity
class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
                .csrf(csrf -> csrf.disable())                                  // для stateless REST API с токенами
                .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/api/auth/**", "/actuator/health").permitAll()
                        .requestMatchers("/api/admin/**").hasRole("ADMIN")
                        .anyRequest().authenticated())
                .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
                .build();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
```

Права можно проверять и на методах: `@PreAuthorize("hasRole('ADMIN') or #userId == authentication.principal.id")`.

## Пароли

Пароли **никогда не хранят в открытом виде** и не шифруют обратимо. Хранят результат медленной адаптивной хеш-функции с солью: **BCrypt**, Argon2, scrypt.

- **соль** — случайная добавка, своя для каждого пароля: одинаковые пароли дают разные хеши, заранее вычисленные таблицы бесполезны;
- **медленность** — перебор миллиардов вариантов становится непрактичным.

Быстрые хеши (MD5, SHA-256) для паролей не подходят именно потому, что они быстрые.

## Сессии и JWT

**Сессия**: сервер хранит состояние, клиент получает cookie с идентификатором. Просто, легко отозвать, но требует общего хранилища сессий при нескольких серверах.

**JWT** (JSON Web Token): сервер подписывает токен с данными о пользователе, клиент присылает его в заголовке `Authorization: Bearer <токен>`. Сервер проверяет подпись и ничего не хранит (stateless).

Токен состоит из трёх частей в Base64: `заголовок.полезная_нагрузка.подпись`.

> **Важно.** Содержимое JWT **не зашифровано**, а только подписано: прочитать его может кто угодно. Не кладите в токен пароли и личные данные. Подделать содержимое нельзя — не сойдётся подпись.

Недостаток JWT — его трудно отозвать до истечения срока. Поэтому access-токен делают короткоживущим (минуты) и выдают в пару к нему долгоживущий refresh-токен.

## Частые уязвимости

- **SQL-инъекция** — склейка запроса из пользовательского ввода. Защита: параметризованные запросы (JPA и `JdbcTemplate` делают это сами; опасна только ручная конкатенация строк).
- **XSS** — внедрение скрипта в страницу. Защита: экранирование вывода.
- **CSRF** — запрос от имени пользователя с чужого сайта; актуален при аутентификации через cookie.
- **CORS** — политика браузера, ограничивающая запросы между разными источниками; настраивается на сервере. Это не защита API, а правило для браузеров.
- **Секреты в репозитории** и излишне подробные сообщения об ошибках.

## Тестирование

| Вид | Что проверяет | Инструменты |
|---|---|---|
| Модульные (unit) | один класс, зависимости заменены заглушками | JUnit 5, Mockito, AssertJ |
| Срезовые | один слой с частью контекста | `@WebMvcTest` (контроллеры), `@DataJpaTest` (репозитории) |
| Интеграционные | приложение целиком | `@SpringBootTest`, Testcontainers (настоящая база в Docker) |

```java
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock OrderRepository repository;
    @InjectMocks OrderService service;

    @Test
    void throwsWhenOrderNotFound() {
        when(repository.findById(42L)).thenReturn(Optional.empty());

        assertThatThrownBy(() -> service.findById(42L)).isInstanceOf(NotFoundException.class);
    }
}
```

Благодаря внедрению через конструктор сервис тестируется без Spring — такие тесты выполняются за миллисекунды. `@SpringBootTest` поднимает весь контекст и работает секунды, поэтому таких тестов должно быть меньше («пирамида тестирования»).

**Mock** — объект-заглушка с запрограммированным поведением и проверкой вызовов. `@MockBean` (в новых версиях `@MockitoBean`) подменяет бин в контексте Spring.

## Что ещё спросят у джуниора

- **Сборка**: Maven (`pom.xml`, фазы `compile → test → package → install`) или Gradle.
- **Docker**: образ, контейнер, `Dockerfile`, `docker compose` для локального окружения.
- **Логирование**: SLF4J + Logback, уровни `ERROR / WARN / INFO / DEBUG`; не пишите в лог пароли и токены.
- **Actuator**: `/actuator/health`, метрики.
- **Миграции базы**: Flyway или Liquibase.
- **HTTP-клиенты**: `RestClient`, `WebClient`, OpenFeign.
- **Очереди сообщений**: Kafka, RabbitMQ — хотя бы назначение.

@@ q
Чем аутентификация отличается от авторизации?
- [ ] Это синонимы
- [x] Аутентификация устанавливает, кто пользователь; авторизация — что ему разрешено
- [ ] Авторизация выполняется раньше аутентификации
- [ ] Аутентификация нужна только администраторам
@@ explain
Сначала система выясняет личность (401 при неудаче), затем проверяет права на конкретное действие (403 при неудаче).

@@ q
Как правильно хранить пароли пользователей?
- [ ] В открытом виде в отдельной таблице
- [ ] Зашифрованными AES с ключом в конфигурации
- [ ] В виде хеша MD5
- [x] В виде хеша BCrypt или Argon2 с солью
@@ explain
Нужна необратимая, медленная функция с уникальной солью. Обратимое шифрование раскрывает все пароли при утечке ключа, а быстрые хеши перебираются миллиардами в секунду.

@@ q
Можно ли хранить в JWT конфиденциальные данные, например номер паспорта?
- [ ] Да, токен зашифрован
- [x] Нет: содержимое токена только закодировано в Base64 и подписано, его может прочитать любой
- [ ] Да, если подпись длинная
- [ ] Да, если токен передаётся в заголовке
@@ explain
Подпись защищает от подделки, но не от чтения. В токен кладут идентификатор пользователя, роли и срок действия.

@@ q
Что защищает от SQL-инъекций?
- [ ] Хранение паролей в BCrypt
- [x] Параметризованные запросы вместо склейки строк с пользовательским вводом
- [ ] Использование HTTPS
- [ ] Длинные имена таблиц
@@ explain
При параметризованном запросе данные передаются отдельно от текста SQL и не могут изменить его структуру.

@@ q
Чем модульный тест сервиса с Mockito отличается от теста с `@SpringBootTest`?
- [ ] Ничем
- [x] Модульный тест не поднимает контекст Spring, проверяет один класс и выполняется за миллисекунды
- [ ] `@SpringBootTest` нельзя использовать с базой данных
- [ ] Модульные тесты не могут проверять исключения
@@ explain
Модульные тесты быстрые и точечные, интеграционные — медленные, но проверяют совместную работу компонентов. Нужны оба вида, первых — больше.
