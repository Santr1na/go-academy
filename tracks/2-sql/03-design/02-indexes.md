## Зачем нужен индекс

Без индекса база читает таблицу целиком и проверяет каждую строку — это **полный просмотр** (full scan, sequential scan). Для миллиона строк — миллион проверок.

**Индекс** — отдельная структура, обычно **B-дерево**: значения столбца хранятся отсортированными вместе со ссылками на строки. Поиск в нём — как поиск слова в словаре: O(log n). Для миллиона строк — около 20 шагов.

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id);
CREATE UNIQUE INDEX idx_customers_email ON customers (email);
```

Первичный ключ и `UNIQUE`-ограничения создают индекс автоматически. А вот для **внешних ключей** в PostgreSQL индекс сам не создаётся — и это частая причина медленных `JOIN`.

## Цена индекса

Индекс ускоряет чтение, но замедляет запись: при каждом `INSERT`, `UPDATE`, `DELETE` его нужно обновить. Ещё он занимает место на диске. Поэтому индексы создают под реальные запросы, а не «на каждый столбец».

Хорошие кандидаты: столбцы из `WHERE`, `JOIN … ON`, `ORDER BY`, внешние ключи. Плохие: столбцы с малым числом разных значений (пол, булев флаг) — индекс почти не сужает поиск, и базе выгоднее прочитать таблицу подряд.

## Составной индекс и правило левого префикса

```sql
CREATE INDEX idx_orders_cust_date ON orders (customer_id, created_at);
```

Составной индекс отсортирован сначала по первому столбцу, внутри — по второму, как телефонная книга по фамилии и имени. Отсюда правило:

| Условие запроса | Индекс `(customer_id, created_at)` |
|---|---|
| `customer_id = 5` | ✅ используется |
| `customer_id = 5 AND created_at > '2024-01-01'` | ✅ используется полностью |
| `created_at > '2024-01-01'` | ❌ первый столбец не задан |

Найти в телефонной книге всех Иванов без фамилии нельзя — только пролистав её целиком. Порядок столбцов в индексе важен: сначала те, по которым ищут на равенство, затем — по диапазону.

## Когда индекс не используется

```sql
WHERE LOWER(email) = 'a@b.c'           -- функция над столбцом
WHERE salary * 12 > 1000000            -- выражение над столбцом
WHERE name LIKE '%ов'                  -- шаблон начинается с %
WHERE phone = 12345                    -- неявное приведение типа (phone — текст)
```

Индекс хранит исходные значения столбца, а запрос спрашивает про преобразованные. Перепишите условие так, чтобы столбец стоял «голым»: `salary > 1000000 / 12`, либо создайте индекс по выражению.

## Покрывающий индекс

Если все нужные запросу столбцы есть в индексе, база вообще не читает таблицу — это самый быстрый вариант (index only scan).

## EXPLAIN

Не гадайте — смотрите **план запроса**:

```sql
EXPLAIN QUERY PLAN                     -- SQLite; в PostgreSQL — EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 1;
```

| Строка плана | Что значит |
|---|---|
| `SCAN orders` (`Seq Scan` в PostgreSQL) | полный просмотр таблицы |
| `SEARCH orders USING INDEX …` (`Index Scan`) | поиск по индексу |
| `USING COVERING INDEX` (`Index Only Scan`) | хватило одного индекса |

## Проблема N+1

Частый вопрос на собеседовании Java-разработчика. Приложение одним запросом загружает список из N заказов, а затем для каждого отдельным запросом — покупателя. Итого N+1 обращение к базе вместо одного. Лечится одним запросом с `JOIN` (в Hibernate — `JOIN FETCH` или `@EntityGraph`) либо загрузкой пачкой через `IN (…)`.

@@ quiz
@@ q
Есть индекс `(last_name, first_name)`. Какой запрос **не сможет** эффективно его использовать?
- [ ] `WHERE last_name = 'Иванов'`
- [ ] `WHERE last_name = 'Иванов' AND first_name = 'Пётр'`
- [x] `WHERE first_name = 'Пётр'`
- [ ] `WHERE last_name LIKE 'Ив%'`
@@ explain
Правило левого префикса: составной индекс отсортирован сначала по `last_name`. Без условия на первый столбец нужные записи разбросаны по всему индексу.

@@ q
По столбцу `email` есть индекс. Почему запрос работает медленно?
```sql
SELECT * FROM users WHERE LOWER(email) = 'anna@example.com';
```
- [ ] `SELECT *` отключает индексы
- [x] К столбцу применена функция, и обычный индекс по `email` использовать нельзя
- [ ] Индексы не работают со строками
- [ ] Не хватает `ORDER BY`
@@ explain
В индексе лежат исходные значения, а сравнивается результат `LOWER(email)`. Решения: индекс по выражению `LOWER(email)` или хранение адреса сразу в нижнем регистре.

@@ q
Какой недостаток у большого числа индексов на таблице?
- [ ] Запросы `SELECT` становятся медленнее
- [x] Замедляются `INSERT`, `UPDATE`, `DELETE` и растёт объём на диске
- [ ] Нарушается целостность данных
- [ ] Таблицу нельзя будет изменить
@@ explain
Каждый индекс нужно обновлять при любом изменении данных. Индексы — компромисс между скоростью чтения и скоростью записи.

@@ q
Что такое проблема N+1?
- [ ] В таблице на одну строку больше, чем ожидалось
- [x] Один запрос за списком и ещё по одному запросу на каждый элемент списка
- [ ] Индекс содержит на один столбец больше нужного
- [ ] Ошибка на единицу в `LIMIT`
@@ explain
Вместо одного запроса с `JOIN` приложение делает N+1 обращение к базе. На списке из тысячи элементов это тысяча лишних сетевых вызовов.

@@ q
Для какого столбца индекс принесёт меньше всего пользы?
- [ ] `email` — у всех пользователей разный
- [ ] `created_at` — по нему часто фильтруют диапазон
- [x] `is_active` — принимает всего два значения
- [ ] `customer_id` — внешний ключ, используется в `JOIN`
@@ explain
У столбца с низкой селективностью условие отбирает примерно половину таблицы — базе выгоднее прочитать её подряд, чем прыгать по ссылкам из индекса.
