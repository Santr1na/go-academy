## Транзакция

Перевод денег — это два изменения: списать с одного счёта и зачислить на другой. Если после первого сервер упадёт, деньги исчезнут. **Транзакция** объединяет несколько команд в одну неделимую операцию.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;        -- зафиксировать; ROLLBACK — отменить всё с момента BEGIN
```

## ACID

Четыре свойства транзакций — обязательный вопрос собеседования.

| Буква | Свойство | Смысл |
|---|---|---|
| **A** | Atomicity — атомарность | выполняются все изменения или ни одного |
| **C** | Consistency — согласованность | данные переходят из одного корректного состояния в другое; ограничения не нарушаются |
| **I** | Isolation — изолированность | параллельные транзакции не мешают друг другу |
| **D** | Durability — долговечность | после `COMMIT` изменения не пропадут даже при сбое питания |

## Аномалии параллельной работы

Полная изоляция обходится дорого, поэтому базы позволяют её ослаблять. Что при этом может пойти не так:

- **Грязное чтение** (dirty read) — транзакция видит незафиксированные изменения другой, которые та потом откатит.
- **Неповторяющееся чтение** (non-repeatable read) — два одинаковых `SELECT` в одной транзакции дают разные значения: между ними строку изменила и зафиксировала другая транзакция.
- **Фантомное чтение** (phantom read) — повторный запрос по условию возвращает новые строки, вставленные другой транзакцией.
- **Потерянное обновление** (lost update) — две транзакции прочитали одно значение, каждая вычислила новое и записала; одно из изменений затёрто.

## Уровни изоляции

| Уровень | Грязное чтение | Неповторяющееся чтение | Фантомы |
|---|---|---|---|
| READ UNCOMMITTED | возможно | возможно | возможны |
| **READ COMMITTED** | нет | возможно | возможны |
| REPEATABLE READ | нет | нет | возможны по стандарту |
| SERIALIZABLE | нет | нет | нет |

По умолчанию в PostgreSQL и Oracle — READ COMMITTED, в MySQL (InnoDB) — REPEATABLE READ. Чем выше уровень, тем меньше аномалий и тем ниже параллелизм (больше ожиданий и откатов).

## Потерянное обновление на практике

```sql
-- обе транзакции одновременно:
SELECT stock FROM products WHERE id = 1;          -- обе видят 5
UPDATE products SET stock = 4 WHERE id = 1;       -- обе записывают 4, хотя продано две штуки
```

Способы защиты:

1. **Атомарное изменение** — пусть считает база: `UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock > 0;`
2. **Пессимистическая блокировка** — `SELECT … FOR UPDATE` блокирует строку до конца транзакции; остальные ждут.
3. **Оптимистическая блокировка** — столбец `version`: `UPDATE … SET stock = 4, version = version + 1 WHERE id = 1 AND version = 7`. Если обновлено 0 строк — кто-то успел раньше, операцию повторяют. В JPA это аннотация `@Version`.

Оптимистический вариант хорош, когда конфликты редки; пессимистический — когда часты.

## MVCC и блокировки

PostgreSQL, Oracle и InnoDB используют **MVCC** — многоверсионность: при изменении создаётся новая версия строки, а читатели продолжают видеть старую. Поэтому читатели не блокируют писателей, а писатели — читателей. Блокируют друг друга только две записи в одну строку.

Две транзакции, захватившие строки в разном порядке, образуют **deadlock**. База обнаруживает его сама и откатывает одну из транзакций с ошибкой — приложение должно быть готово повторить операцию. Профилактика та же, что в Java: единый порядок захвата и короткие транзакции.

> **Важно.** Не держите транзакцию открытой, пока приложение ходит по сети или ждёт пользователя: она удерживает блокировки и соединение с базой.

@@ q
Какой уровень изоляции используется по умолчанию в PostgreSQL?
- [ ] READ UNCOMMITTED
- [x] READ COMMITTED
- [ ] REPEATABLE READ
- [ ] SERIALIZABLE
@@ explain
READ COMMITTED: каждый запрос видит данные, зафиксированные к моменту его начала. В MySQL InnoDB по умолчанию REPEATABLE READ.

@@ q
Что такое оптимистическая блокировка?
- [ ] Блокировка всей таблицы на время транзакции
- [ ] `SELECT … FOR UPDATE`
- [x] Проверка версии строки при обновлении: если версия изменилась, операция отклоняется

@@ explain
Строки не блокируются; конфликт обнаруживается в момент записи по столбцу версии. В JPA — `@Version` и `OptimisticLockException`.

@@ q

- [ ] База данных будет восстановлена из резервной копии

Атомарность: транзакция либо фиксируется целиком, либо откатывается целиком.
