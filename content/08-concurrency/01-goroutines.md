## Горутина

Горутина — функция, выполняющаяся **конкурентно** с остальным кодом. Запускается ключевым словом `go`:

```go
func say(s string) {
	for range 3 {
		fmt.Println(s)
		time.Sleep(100 * time.Millisecond)
	}
}

func main() {
	go say("мир")   // запуск в новой горутине
	say("привет")   // в текущей
}
```

Горутины очень дёшевы: стартовый стек ~2–8 КБ (растёт динамически), создание — сотни наносекунд. Программа может держать сотни тысяч горутин.

> **Важно:** когда `main` возвращается, программа завершается **сразу**, не дожидаясь остальных горутин.

## Планировщик: модель GMP

- **G** (goroutine) — горутина;
- **M** (machine) — поток ОС;
- **P** (processor) — логический процессор с очередью горутин; их число = `GOMAXPROCS` (по умолчанию — число ядер, с Go 1.25 учитываются и cgroup-лимиты контейнера).

Планировщик распределяет множество G по небольшому числу M. Когда горутина блокируется (канал, мьютекс, сеть), её место занимает другая. Есть work stealing: свободный P «крадёт» горутины у загруженного. С Go 1.14 планировщик вытесняющий — даже бесконечный цикл без вызовов функций не заблокирует остальных.

**Конкурентность** — структура программы как набора независимых задач. **Параллелизм** — их одновременное выполнение на нескольких ядрах. Конкурентный код может работать и на одном ядре.

## sync.WaitGroup

Чтобы дождаться завершения группы горутин:

```go
var wg sync.WaitGroup
for i := range 5 {
	wg.Add(1)            // ДО запуска горутины
	go func() {
		defer wg.Done()  // уменьшить счётчик при выходе
		fmt.Println("работник", i)
	}()
}
wg.Wait()                // блокируется, пока счётчик не станет 0
```

С Go 1.25 есть удобный метод `wg.Go(f)`, который сам делает `Add(1)` и `defer Done()`:

```go
for i := range 5 {
	wg.Go(func() { fmt.Println("работник", i) })
}
wg.Wait()
```

Правила:

1. `Add` вызывайте **до** `go`, а не внутри горутины — иначе `Wait` может завершиться раньше, чем горутина успеет сделать `Add`.
2. `WaitGroup` нельзя копировать — передавайте указатель.
3. Количество `Done` должно точно совпадать с `Add`, иначе `Wait` зависнет или будет паника «negative counter».

## Сбор результатов без гонки

Каждая горутина пишет в **свой** элемент заранее созданного среза — это безопасно, потому что элементы разные:

```go
results := make([]int, len(inputs))
var wg sync.WaitGroup
for i, x := range inputs {
	wg.Go(func() {
		results[i] = heavy(x)
	})
}
wg.Wait()
```

А вот `append` в общий срез или запись в общую map из нескольких горутин — **гонка данных**. Её решают мьютексом или каналом (следующие уроки).

## Разбираем подробнее: как думать о конкурентном коде

Обычная программа — один исполнитель, который идёт по строкам сверху вниз. Слово `go` добавляет **второго исполнителя**, который начинает работать с указанной функции, пока первый идёт дальше. С этого момента у вас нет гарантий, кто из них что сделает раньше.

```go
func main() {
	go fmt.Println("из горутины")
	fmt.Println("из main")
}
```

Что может произойти:

| Сценарий | Вывод |
|---|---|
| `main` завершилась раньше, чем горутина успела стартовать | только `из main` |
| горутина успела первой | `из горутины`, затем `из main` |
| горутина успела после печати `main`, но до выхода | `из main`, затем `из горутины` |

Все три варианта возможны, и на вашем компьютере почти всегда будет первый. **Программа завершается, когда завершается `main`** — остальные горутины никто не ждёт. Отсюда первое правило: если результат горутины нужен, её завершения надо **явно дождаться**.

### WaitGroup: счётчик незавершённых работ

```go
var wg sync.WaitGroup
for i := 0; i < 3; i++ {
	wg.Add(1) // «выдал ещё одну работу» — ДО запуска горутины
	go func() {
		defer wg.Done() // «работа закончена» — на любом пути выхода
		fmt.Print(i)
	}()
}
wg.Wait() // блокируется, пока счётчик не станет нулём
```

Программа напечатает цифры 0, 1 и 2 — но **в произвольном порядке**: `012`, `201`, `120`… Каждая горутина видит своё значение `i` (с Go 1.22), а вот очерёдность выполнения никто не обещал.

Три ошибки, которые делают почти все:

- **`wg.Add(1)` внутри горутины.** `main` может дойти до `Wait` раньше, чем горутина успеет выполнить `Add`, — счётчик будет нулевым, и `Wait` вернётся сразу.
- **WaitGroup передана по значению.** `func work(wg sync.WaitGroup)` получает **копию** счётчика. `Done` уменьшит копию, оригинал останется на единице — `Wait` повиснет навсегда: `fatal error: all goroutines are asleep - deadlock!`. Передавайте `*sync.WaitGroup`.
- **Забытый `Done`** на одном из путей (например, при раннем `return`). Лекарство — `defer wg.Done()` первой строкой.

### Гонка данных

```go
n := 0
var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		n++ // читаем, прибавляем, записываем — три шага, а не один
	}()
}
wg.Wait()
fmt.Println(n) // 1000? Не обязательно: 987, 994, 1000…
```

`n++` — не одно действие, а три: прочитать, прибавить, записать. Две горутины могут прочитать одно и то же старое значение, обе прибавят единицу и обе запишут один и тот же результат — одно увеличение потеряется. Это **гонка данных** (data race): несколько горутин работают с одной переменной, и хотя бы одна пишет.

Гонки коварны тем, что программа обычно «работает» — и ломается раз в неделю на боевом сервере. Способов защиты три, им посвящены следующие уроки: мьютекс, атомарные операции и каналы.

### Паника в горутине роняет всю программу

```go
func main() {
	defer func() { recover() }() // не поможет
	go func() { panic("boom") }()
	time.Sleep(100 * time.Millisecond)
}
```

`recover` перехватывает панику только **в той же горутине**. Паника в любой другой горутине завершает программу целиком. Поэтому в долгоживущих сервисах `defer`+`recover` ставят в начале каждой запускаемой горутины.

### Горутина должна уметь завершиться

Горутину нельзя остановить снаружи. Если она ждёт данных, которые никогда не придут, она останется висеть до конца работы программы — это **утечка горутин**. Запуская горутину, всегда отвечайте себе на вопрос: «при каких условиях она закончится?».

@@ task parallel-sum | Параллельная сумма | xp=50
Реализуйте `ParallelSum(nums []int, parts int) int`: разбейте срез на `parts` примерно равных частей, посчитайте сумму каждой части **в отдельной горутине**, дождитесь всех через `sync.WaitGroup` и сложите частичные суммы.

Если `parts <= 0`, используйте 1. Если частей больше, чем элементов, — лишние части просто пустые.

Каждая горутина должна писать в **свой** элемент среза `partial` — так не будет гонки.

`partial := make([]int, parts)`; в горутине `for _, v := range nums[lo:hi] { partial[i] += v }`.

package main

import (
	"fmt"
	"sync"
)

func ParallelSum(nums []int, parts int) int {
	if parts <= 0 {
		parts = 1
	}
	size := (len(nums) + parts - 1) / parts
	partial := make([]int, parts)
	var wg sync.WaitGroup
	for i := range parts {
		lo := min(i*size, len(nums))
		hi := min(lo+size, len(nums))
		wg.Add(1)
		go func() {
			defer wg.Done()
			for _, v := range nums[lo:hi] {
				partial[i] += v
			}
		}()
	}
	wg.Wait()
	total := 0
	for _, s := range partial {
		total += s
	}
	return total
}

func main() {
	nums := make([]int, 1000)
	for i := range nums {
		nums[i] = i + 1
	}
	fmt.Println(ParallelSum(nums, 4))
}

@@ task parallel-map | Параллельный Map | xp=50 interview
Реализуйте `ParallelMap(xs []int, f func(int) int) []int` — применяет `f` к каждому элементу **конкурентно** (по горутине на элемент) и возвращает результаты **в исходном порядке**.

Тест проверит, что функция действительно работает параллельно: 20 вызовов `f`, каждый из которых спит 50 мс, должны завершиться значительно быстрее секунды.
@@ hint
`res := make([]int, len(xs))` и в каждой горутине `res[i] = f(x)`.
@@ hint
Не забудьте `wg.Wait()` перед возвратом. Можно использовать `wg.Go(func() { ... })` (Go 1.25+).

@@ solution
package main

import (
	"fmt"
	"sync"
)

func ParallelMap(xs []int, f func(int) int) []int {
	res := make([]int, len(xs))
	var wg sync.WaitGroup
	for i, x := range xs {
		wg.Go(func() {
			res[i] = f(x)
		})
	}
	wg.Wait()
	return res
}

func main() {
	fmt.Println(ParallelMap([]int{1, 2, 3}, func(x int) int { return x * x }))
}

package main

import (
	"fmt"
	"testing"
	"time"
)

func TestParallelMapResult(t *testing.T) {
	got := ParallelMap([]int{1, 2, 3, 4}, func(x int) int { return x * 10 })
	if fmt.Sprint(got) != "[10 20 30 40]" {
		t.Errorf("результат %v, ожидалось [10 20 30 40]", got)
	}
	if len(ParallelMap(nil, func(x int) int { return x })) != 0 {
		t.Error("для пустого входа ожидался пустой результат")
	}
}

func TestParallelMapIsConcurrent(t *testing.T) {
	xs := make([]int, 20)
	for i := range xs {
		xs[i] = i
	}
	start := time.Now()
	got := ParallelMap(xs, func(x int) int {
		time.Sleep(50 * time.Millisecond)
		return x + 1
	})
	elapsed := time.Since(start)
	if elapsed > 600*time.Millisecond {
		t.Errorf("выполнение заняло %v — похоже, вызовы идут последовательно (ожидалось ~50мс)", elapsed)
	}
	for i, v := range got {
		if v != i+1 {
			t.Fatalf("порядок нарушен: res[%d] = %d", i, v)
		}
	}
}
